# 四报告审核流程 × 报告模板审核配置可行性分析

> 生成日期：2026-07-29（状态机层已于 2026-07-29 晚实现，见文末「已实现」标注）
> 目的：① 梳理信息核验 / 信用风控 / 欺诈识别方案4 / 决策报告 四个报告**真实的审核流程（状态机）**；② 判断"报告模板"里的审核配置（businessFlow / flowGraph）**能否把这些流程配出来**。

---

## 0. 核心结论（先看这个）

**已实现**：模板审核配置现在既能配出"审批弹窗内容"，也能配出"完整审核状态机"。

- ✅ **弹窗内容层**：`flowGraph.manual` 节点配置「审核事项 / 审批结果 / 审批意见」，经 `getAuditFlow()` + `ApprovalModal` 命中四报告（含 credit 真实页，已补接）。
- ✅ **状态机层（2026-07-29 晚实现）**：新增 `FlowStateMachine` 模型 + `resolveActions()` 查表，把四报告的「按钮可见性矩阵 + 状态流转」从各自 `opsFor` 硬编码改为**由模板状态机配置驱动**；并在 `ReportTemplate` 配置页用画布可视化（节点=状态、连线=跳转）。详见 §3/§4 更新与文末「已实现」段。

> 历史结论（实现前）：原状态机层为 ❌，四报告矩阵全硬编码在 `opsFor` 类函数；现已消除该 gap。

## 1. 模板审核配置现状（能配什么）

数据模型位于 `reportTemplateData.ts`：

| 模型要素 | 类型 / 字段 | 现状 |
|---|---|---|
| 分段流程配置 | `BusinessFlowConfig`（含 `flowGraph?: FlowGraph`） | 每个报告类型一份 `businessFlow[]`，第 0 行占位，其后每行对应一个评分分段（grade） |
| 画布流程图 | `FlowGraph`（`nodes`/`edges`）+ `FlowGraphNode` | 节点含 `type`（start/manual/auto/notify/end）、`role`、`signMode`、`checkItems`、`results`、`opinionPresets`、`autoAction`、`cond`、`timeout*` 等 |
| 审批弹窗输出 | `getAuditFlow(type, grade): AuditFlow`（`nodeLabel`/`checkItems`/`results`/`opinionPresets`） | 取该分段 `flowGraph` 中 results 最多的 `manual` 节点；无则兜底 |
| 实际弹窗 | `ApprovalModal`（审核事项 → 审批结果 → 审批意见 → 附件） | 已被 info_verify / fraud / decision 的详情页"审批"按钮接入 |

已落地的 `FLOW_PRESETS` 分段内容：

| 报告 | 分段（grade） | 自动结果 | 已配审核事项 / 审批结果 |
|---|---|---|---|
| info_verify | 安全 / 关注 / 警示 / 高危 | 通过 / 转人工 / 转人工 / 拒绝 | 身份真实性核验、设备群控核查、黑名单命中复核… |
| credit | A / B / C / D | 通过 / 通过 / 转人工 / 拒绝 | 征信报告复核、偿债能力评估… |
| fraud | 极低 / 低 / 中 / 高 / 极高 | 通过 / 通过 / 转人工 / 拒绝 / 拒绝 | 反欺诈规则复核、团伙欺诈核查… |
| decision | 优先通过 / 通过 / 限制额度 / 严格限制 / 拒绝 | 通过 / 通过 / 转人工 / 拒绝 / 拒绝 | 三项子报告一致性核对、信用与欺诈综合研判… |

**模板现在"配得出来"的**：审核事项清单、审批结果集（通过/驳回/拒绝）、按结果分组的意见预设、节点角色/会签/超时（字段有，但弹窗未消费）、自动处置标签。
**模板现在"配不出来"的**：状态机（按钮可见性矩阵）、状态流转、角色-状态-按钮权限、条件分支真正触发动作（见 §3）。

## 2. 四报告真实审核流程（逐个状态机）

### 2.1 信息核验（info_verify）— `VerifyOps.tsx`
- **系统自动结果 `SysResult`**：处理中 / 通过 / 拒绝 / 预警
- **人工状态 `WorkStatus`**：核验计算中 / 待确认 / 已确认 / 待审核 / 提交复核 / 复核通过 / 复核拒绝 / 强制放行

矩阵 `opsFor(sys, work, includeAudit)`（includeAudit=true 为详情页）：

| 系统结果 | 人工状态 | 详情页按钮（已收敛） | 列表页按钮 |
|---|---|---|---|
| 计算中 | 核验计算中 | 查看（锁） | 查看（锁） |
| 通过 | 待确认 | 查看、**审批** | 查看、报告确认 |
| 通过 | 已确认 | 查看 | 查看 |
| 拒绝 | 待确认 | 查看、**审批**、强制复审 | 查看、报告确认、强制复审 |
| 拒绝 | 已确认 / 强制放行 | 查看 | 查看 |
| 预警 | 待审核 | 查看、提交双人复核 | 查看、提交双人复核 |
| 预警 | 提交复核 | 查看、**审批** | 查看、确认放行、确认拒绝 |
| — | 复核通过 / 复核拒绝 | 查看 | 查看 |

- 详情页"审批"弹窗内容 = `getAuditFlow('info_verify', grade)`（grade 由真实异常值经 `ivGradeFromRisk` 推得）。
- 保留的专业操作：**强制复审**（推翻拦截）、**提交双人复核**。
- ✅ 已接入模板审批弹窗。

### 2.2 欺诈识别方案4（fraud）— `FraudScheme4Ops.tsx`
- **风险等级 `scoreBand`**：极低 / 低 / 中 / 高 / 极高
- **人工状态 `FraudS4WorkStatus`**：核验计算中 / 待确认 / 已确认 / 初审拒贷 / 强制放行 / 加入黑名单 / 待审核 / 提交复核 / 复核通过 / 复核拒绝-拒绝办结

矩阵 `fraudScheme4OpsFor(work, band)`（详情页 `consolidateAudit=true` 把 报告确认/确认放行/确认拒绝 收敛为"审批"）：

| 人工状态 | 风险等级 | 详情页按钮（已收敛） |
|---|---|---|
| 核验计算中 | — | 查看（锁） |
| 待确认 | 极低 / 低 | 查看、**审批** |
| 待确认 | 高 | 查看、**审批**、强制复审 |
| 待确认 | 极高 | 查看、**审批**、加入黑名单 |
| 已确认 / 初审拒贷 / 强制放行 / 加入黑名单 / 复核通过 / 复核拒绝-办结 | — | 查看 |
| 待审核 | 中 | 查看、提交双人复核、录入备注 |
| 提交复核 | 中 | 查看、**审批**、录入备注 |

- "审批"弹窗内容 = `getAuditFlow('fraud', band)`。
- 保留的专业操作：**强制复审 / 提交双人复核 / 加入黑名单 / 录入备注**。
- 列表页不变（仍用原始 报告确认/确认放行/确认拒绝）。
- ✅ 已接入模板审批弹窗。

### 2.3 信用风控（credit，真实页 CreditKimiDetail）— `CreditKimiOps.tsx`
- **系统自动结果 `CreditSysResult`**：处理中 / 通过 / 拒绝 / 预警
- **人工状态 `CreditWorkStatus`**：待审核 / 提交复核 / 复核放行 / 复核拒绝（注：信用报告无"待确认/已确认/强制放行"等概念，流程更短）

矩阵 `creditOpsFor(sys, work)`：

| 系统结果 | 人工状态 | 按钮 |
|---|---|---|
| 处理中 | — | 查看（锁） |
| 通过 / 拒绝 | — | 查看 |
| 预警 | 待审核 | 查看、提交复核、录入备注 |
| 预警 | 提交复核 | 查看、确认放行、确认拒绝、录入备注 |
| — | 复核放行 / 复核拒绝 | 查看 |

- ⚠️ **尚未接入模板审批弹窗**：`CreditOpKey` 只有 `view/submitReview/confirmPass/confirmReject/note`，**没有 `audit`**，提交复核 / 确认放行 / 确认拒绝 仍是硬编码弹窗，内容**不是**从 `businessFlow` 配出。
- 原因：之前把"4 按钮→单一审批"收敛做在了**已删除的废弃页 `CreditReportDetail`** 上，平移到真实页 `CreditKimiOps` 是待办项（见 §5）。
- 信用报告没有"报告确认 / 强制复审 / 加入黑名单"这类概念，其流程天然最短。

### 2.4 决策报告（decision）— `DecisionOps.tsx`
决策报告是**双层审核**：

**(A) 子报告人工审核状态**（`reviewOpsFor(m: ManualReview, s: DecisionSuggestion)`）：

| 人工状态 | 综合建议 | 按钮 |

| 核验计算中 | — | 查看（锁） |
| 待确认 | 通过 | 查看、报告确认 |
| 待确认 | 严格限制 | 查看、报告确认、强制复审 |
| 待确认 | 拒绝 | 查看、报告确认、加入黑名单 |
| 已确认 / 初审拒贷 / 强制放行 / 复核通过 / 复核拒绝 / 加入黑名单 | — | 查看 |
| 待审核 | — | 查看、提交双人复核、录入备注 |
| 提交复核 | — | 查看、确认放行、确认拒绝、录入备注 |

**(B) 综合决策审批**（`decisionOpsFor(_s, w: ApprovalStatus)`）：

| 审批状态 | 按钮 |

- ✅ 已接入模板审批弹窗。

## 5. 若要做到"审核流程也能由模板配出来"，需补的模型

要让四个报告的审核流程真正"配出来"，需新增一层**状态机模型**并让报告消费它：

1. **新增状态机定义**（建议挂在 `ReportTemplate` 或独立的 `flowMachine` 上）：
   - `states: { id; label; isTerminal; autoResult? }[]`
   - `transitions: { from; action; to; role?; autoResult?; condition? }[]`
   - 每个 `action`（按钮）的 `label` / 是否打开 `ApprovalModal` / 打开时取哪个分段的 `flowGraph`。
2. **把 `opsFor` 改为查表**：四个报告各自的 `*OpsFor` 改为从状态机定义运行时计算可见按钮与次态，删除硬编码矩阵。
3. **画布与状态机绑定**：现有 `FlowGraph` 画布节点 = 状态、连线 = 转移，编辑即改状态机；`autoAction`/`cond` 真正接入执行（或至少驱动自动结果字段）。
4. **角色权限矩阵**：在 `transitions` 上加 `role` 字段，实现"某角色在某状态可见某按钮"。
5. **信用真实页收尾**：把 §2.3 的"提交复核/确认放行/确认拒绝"收敛为单一"审批"并接 `getAuditFlow('credit', grade)`（与另三报告一致）。

> 注：第 1–4 项属于"模板建模大工程"，与 `报告模板反推分析.md` §三/§四/§八 的模型扩展方向一致，建议合并规划。
