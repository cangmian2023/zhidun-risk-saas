# 信息核验报告 → 报告模板 反向转换方案

> 版本：v1.2　|　日期：2026-08-03　|　范围：`PreVerifyDetail`（信息核验报告详情）↔ `ReportTemplate`（报告模板配置）
>
> 用途：记录「从现有报告详情反推报告模板配置」的完整方案、设计决策与落地状态。后续「从模板生成报告详情」全部依赖本文档的映射口径。

## 一、背景与目标

### 现状问题

平台已有四个报告详情页（信息核验 PreVerify / 信用风控 CreditKimi / 欺诈识别 FraudScheme4 / 决策报告 Decision），但它们**各自硬编码**，与报告模板配置没有真正打通。表现为：

- 报告详情里的标题、分数刻度、卡片结构、结论按钮，改一处就要改一次代码；
- 模板配置页配了半天，详情页看不到任何变化；
- 四个报告的模型各不相同，无法统一维护。

### 目标

以**信息核验报告**为蓝本做一次完整的反向转换，把详情页的每个卡片、每个字段都落位到模板配置项上，建成**标准信息核验报告模板**（`tpl-info-standard`）。跑通之后，再把其余三个报告按同一套模型重建。

### 总体策略

```
第一步：反向转换（本次）
  PreVerifyDetail 逐元素拆解 → 落位到四个配置 Tab
  （报告内容配置 / 自动审核配置 / 人工审核配置 / 基础信息）
  → 建成 tpl-info-standard

第二步：统一（后续）
  信用风控 / 欺诈识别 / 决策报告 三个模板按同一套模型重建
```

## 三、关键设计决策

### 3.1 #13 数据源合集的内部分组（方案 A）

**问题**：用户基本信息卡实际含两个子组——一组无名的基础字段 + 一组「环境采集」字段。反向配成数据源合集时，这个「一卡两组」的层次必须保住。

**两个选项**：

| 方案 | 做法 | 还原度 | 工作量 |
|---|---|---|---|
| A（采纳） | 改造配置模型，数据源合集支持**内部分组并命名** | 完整还原 | 较大 |
| B | 把「环境采集」拆成独立合集，变成另一张卡 | 破坏层次 | 最小 |

**采纳 A**，理由：这是后续所有内容合集的范式，地基不能歪。B 方案会让一张卡变两张，跟原报告对不上。

**落地**：

```ts
export interface FieldGroup { id: string; name: string }

interface SectionConfig {
  // ...
  fieldGroups?: FieldGroup[]   // 合集内部分组
}
// FieldConfig / DbField / ApiOutput 各增 group?: string 指向所属分组
```

用户基本信息 = 1 个合集 + 2 个分组：「基础资料」（11 个字段）+「环境采集」（5 个字段）。

---

### 3.2 #14/#15/#16 三类新合集与 `tpl_copy` 源类型

三张卡分别对应三种不同的合集来源类型：

| 卡片 | 源类型 | 说明 |
|---|---|---|
| 二、用户证件照 | `api` | 入参 `applicantId` / `idCard`，输出容器强制 `image` |
| 三、多源并行核验单项报告 | `rule_set` | 绑定规则集 `rs_identity`，5 条规则 |
| 五、数据交叉融合综合报告 | `tpl_copy` ★新增 | 复用「三」的整套配置 |

**为什么要新增 `tpl_copy`**：第五张卡的结构和第三张完全一致，只是数据来源不同。如果各配一遍，两处配置会逐渐漂移。新增一个「复用其他合集配置」的源类型，让它只读引用：

```ts
export const SECTION_COPY_FROM: Record<string, string> = {
  cross_fusion: 'single_verify',
}
```

`buildSections` 内部引入 `built` 字典，让后构建的合集能引用先构建好的合集。配置页对 `tpl_copy` 显示「集成 N 个列表 · 配置只读」。

### 3.3 #11 结论卡改名与审核状态机

**改名**（消除歧义，让名字直接说明配置来源）：

- 「系统结果」→ **自动审核**：由分数计算判定，对应【自动审核配置】的 `ScoreGrade.autoResult`
- 「工单状态」→ **人工审核**：人工操作后的状态，对应【人工审核配置-业务流程配置】

**卡片标题**：取自模板 `flowBlock.title`，不再硬编码。

**状态机**（用户给定，权威口径）：

```
自动审核三态：通过 / 预警 / 拒绝
    │
    ├─ 通过、拒绝 → 需一级审核员确认
    │     人工状态：待确认 / 确认通过 / 确认拒绝
    │     ⚠️ 拒绝不可直接转通过，通过不可直接转拒绝
    │
    └─ 预警 → 一级审核员「提交复核」→ 二级审核员确认
          人工状态：提交复核 / 复核通过 / 复核拒绝

任一终态之前均可「关闭」→ 状态变「关闭」
```

**落位**：`BusinessFlowConfig`（gradeId/suggestionText）+ `FlowGraph`（nodes/edges/resultStates）+ `getSegmentButtons`（按当前状态出按钮）。按钮不硬编码，由模板的 `businessFlow.flowGraphs` 驱动。

### 3.4 #5 构成项分解表改由特殊命中规则驱动

**原状**：表格数据是硬编码的 `scoreComponents`，与模板毫无关系。

**方案**：该表改由【自动审核配置-特殊命中规则】驱动，**每行 = 一条规则**：

| 表格列 | 来源 |
|---|---|
| 风险维度 | `rule.ruleName` |
| 用户情况 | `${SPECIAL_TRIGGER_LABEL[trigger]}·${sectionName}` |
| 得分 | `rule.score` |
| 权重 | `rule.weight`，缺省取来源分段的 `weight` |
| 等级 | `matchDimBand(得分, dimBands)` |
| 核心因子 | `rule.priority === 'decisive'` |

**模型变更**：`SpecialRule` 增补两个评分构成字段。

```ts
interface SpecialRule {
  // ...
  score?: number    // 该规则命中对异常值的贡献分
  weight?: number   // 该规则所属分段的权重（%），缺省取来源分段 weight
}
```

**兜底**：模板没配特殊规则时，回落到原有数据，不出空表。

### 3.5 #3 阈值刻度条 —— 分值语义开关（★核心决策）

这是本次唯一真正卡住的一项，卡点不是工作量，是**语义打架**：

| | 模板侧（`GRADE_PRESETS.info_verify`） | 详情页侧（原刻度条） |
|---|---|---|
| 语义 | **异常值**，越高越危险 | **信用值**，越高越安全 |
| 段数 | 4 段 | 3 段 |
| 分段 | 0-20 安全 / 21-50 关注 / 51-80 警示 / 81-100 高危 | <20 低信用(红) / 20-80 中(黄) / ≥80 高信用(绿) |

方向相反、段数还不同，直接对接会错得离谱。

#### 三条路的效果对比

**(a) 详情页改成异常值语义，完全跟模板走**

- 效果：大数字从 87 变成 13，刻度条左绿右红，段数变 4 段
- 优点：模型最干净，只有一套语义
- 缺点：客户看到的数字含义整个翻过来了，业务侧要重新解释「13 分是好还是坏」

**(b) 模板加「分值语义」开关，详情页按开关渲染** ← **采纳**

- 效果：评分模型一个字不改，只告诉详情页「这个数要当信用值读」，于是刻度条整条左右翻转、大数字显示 100−13=87
- 优点：**外观跟改造前一模一样，但底下已经全是模板数据**；两种语义都能支持，将来信用/欺诈报告可以各选各的
- 缺点：多一层「语义」概念要理解

**(c) 刻度条改读 `dimBands` 而不是 `grades`** ← **推翻**

- 初判：`dimBands` 天然是低/中/高三段，跟详情页对得上，看似最省事
- **推翻理由**：翻源码注释发现 `dimBands` 写的是「**本维度**独立的三档」——它是给下面那张**维度分布表**用的维度级模型，不是总分模型。拿它画总分刻度条属于借错了东西，能跑但模型错位，后患大。

#### 采纳方案 (b) 的落地

```ts
/* 分值语义：决定报告详情页「大数字 + 阈值刻度条」的读数方向。
 *  - 'risk'   异常值：直接展示总分，越高越危险，刻度条与 grades 同向（左低右高）
 *  - 'credit' 信用值：展示「满分 − 总分」，越高越安全，刻度条整条左右翻转
 * 分段边界 / 配色 / 结论一律取 grades，本开关只管「这个数怎么读」，不改评分模型本身。
 */
export type ScoreSemantic = 'risk' | 'credit'

interface ScoreDisplayConfig {
  // ...
  scoreSemantic?: ScoreSemantic   // 缺省 'risk'
}

/** 把模板分段铺成刻度条；'credit' 语义下整条左右翻转 */
export function buildScoreBar(grades, semantic): { segs, bounds, min, max }

/** 模型原始总分 → 详情页展示值 */
export function toDisplayScore(raw, semantic, grades): number

/** 模型原始总分落在哪个分段 */
export function matchGrade(raw, grades): ScoreGrade | undefined
```

**关键设计原则**：分段边界、配色、结论文案**一律取 `grades`**，语义开关只管「这个数怎么读」，不改评分模型本身。这样两种语义共用同一套评分配置，不会分裂。

**实测效果**（`tpl-info-standard`，语义 = credit）：

```
段序翻转：高危@0%  警示@20%  关注@50%  安全@80%
边界刻度：0 / 19 / 49 / 79 / 100
异常值 13 → 显示 87，指针 87%，命中「安全·风险可控」→ 通过
异常值 90 → 显示 10，指针 10%，命中「高危·极高风险」→ 拒绝
```

徽标显示「安全 · 风险可控」，悬停出该档处置说明；`showThresholdBar` 关掉整条刻度条消失。

配置页「评分方案」Tab 的预览工具条加了**分值语义下拉**，旁边实时显示「详情页读数 87（= 100 − 13）」，可直接切换对比两种效果。

### 4.7 #1/#19 报告标题 —— 所见即所得，不做任何加工

**改前**：`PreVerifyDetail.tsx:475` 硬编码 `title="信息核验报告"`。不管模板名改成什么，详情页顶部永远显示这五个字。

**曾经的纠结（已否决）**：模板名叫「标准信息核验**报告模板**」，直接读 `tpl.name` 会让客户看到带「模板」二字的标题。当时提了两个补救方案 —— ① 字符串裁掉结尾的「模板」二字；② 模板里加一个独立的「报告标题」字段与模板名解耦。

**最终定案：两个都不要，直接读 `tpl.name`。**

```tsx
{/* 报告标题直接取模板名称（基础信息-模板名称*）：用户配什么就显示什么，不做任何裁剪 */}
<DetailHeader title={ivTpl?.name || '信息核验报告'} ... />
```

**决策依据**：这是**配置项的所见即所得原则**。模板名称本来就是用户在「基础信息-模板名称\*」里亲手填的，填什么就该显示什么。

- 否决 ① 的理由：系统偷偷裁字符串，是替用户做决定。用户真想让标题末尾带「模板」二字（比如内部演示模板）也做不到，而且裁剪规则本身就是不可预期的隐式行为。
- 否决 ② 的理由：为一个不存在的问题增加配置项。嫌名字带「模板」二字不好看，用户改一下模板名就完了 —— 这是**用户的输入问题，不是系统的建模问题**。多加一个字段反而让用户面对「模板名 / 报告标题」两个含义相近的框，徒增困惑。

> **沉淀为项目通则**：凡是用户直接输入的文本类配置（模板名、卡片标题、模型名称、字段显示名等），一律原样透传到展示层，不做裁剪、补全、格式化等任何隐式加工。展示不合适 → 让用户改输入，而不是让系统猜意图。

**联动链路**：配置页「模板名称」输入（`ReportTemplate.tsx:1078`）→ `patch` → `templateStore` → 详情页 `useTemplate(undefined, 'info_verify')` → 标题实时刷新。

### 5.1 展示形态贯通 —— 抽出共用组件 `ScoreVisual`（★核心决策）

**原问题**：配置页预览支持四种形态（大数字 / 环形图 / 进度条 / 仪表盘）但不做语义翻转；报告详情页做了语义翻转却**写死只渲染大数字**。两边各画各的，直接后果是「模板里选了环形图，报告里还是大数字」——展示形态这个配置项等于没生效。

**为什么不是"让预览也翻转一下"**：那只是把两份实现改成当下看起来一致，下次任何一边改动又会漂移。所见即所得不能靠人肉对齐，只能靠**结构上不可能不一致**。

**方案**：新建 `src/console/ScoreVisual.tsx`，作为评分可视化的唯一实现，配置页预览与报告详情页共同引用。

```
                 ┌─────────────────────┐
模板 scoreDisplay ─→│    ScoreVisual      │─→ 配置页「评分方案」预览
  displayComponent │  · 四形态渲染        │
  grades           │  · 语义翻转          │─→ 报告详情页评分卡
  scoreSemantic    │  · 阈值刻度条        │
  三个开关          │  · 风险标签/说明     │   （同一份代码，不可能不一致）
                 └─────────────────────┘
```

**坐标系约定**（关键，避免调用方各自换算出错）：
- 入参 `rawScore` 一律是**模型原始分**，与 `grades` 的 `minScore/maxScore` 同坐标系（异常值空间）。
- 语义翻转在组件内部完成，调用方不换算。
- **命中判定始终用 `rawScore` 撞 `grades`**，因此无论展示成哪种语义、哪种形态，落在哪一段、什么颜色、什么自动审核结论都完全一致。

**四种形态统一取同一组读数**（实测，模板语义 = credit）：

| 原始分 | 展示读数 | 指针位置 | 命中分段 | 自动审核 |
|---|---|---|---|---|
| 13 | 87 | 87% | 安全 · 风险可控 | 通过 |
| 35 | 65 | 65% | 关注 · 中等风险 | 转人工 |
| 60 | 40 | 40% | 警示 · 较高风险 | 转人工 |
| 90 | 10 | 10% | 高危 · 极高风险 | 拒绝 |

形态只改画法，不改数——切换大数字/环形图/进度条/仪表盘，上表四列不变。

**配置页保留的差异**：预览区独有「风险等级 / 自动审核结果」内联下拉编辑，通过 `tagSlot` 插槽注入，不影响主体渲染共用。

**副产品**：`ScoreCardPreview` 从 149 行降到 43 行（渲染全部下沉），详情页同时删掉了本地的 `levelText` 映射表与三处手工换算。

### 5.2 模板选取改为遵循「默认模板」标记

**原问题**：`getTemplateByType` 用 `find(reportType === type)` 取**第一个**匹配模板。这不只是"以后调数组顺序会出问题"的隐患，而是**当下就坏着的功能**——配置页「设为默认」按钮弹窗承诺"新进件将使用新模板"，但报告详情页压根不看 `isDefault`，按钮是空操作。

`info_verify` 类型下实际有 2 个模板（标准版 · 已启用 · 默认 / 权威版备用 · 草稿），靠数组顺序碰巧选对。

**两处修复**：

1. `templateStore.getTemplateByType` 取用优先级改为 **默认 → 已启用 → 兜底第一个**，草稿模板不会抢位。
2. `ReportTemplate.setDefault` 补两个缺陷：
   - 默认位改为在**同一 reportType 内互斥**转移（原实现对全部模板置位，会顺手清掉其他报告类型的默认标记）；
   - 同步写回 `seedReportTemplates` 并 `touch()`，详情页才感知得到（此前只改了配置页本地 state）。

### 5.3 sections 数组统一访问（2026-08-03）

**动机**：模板 sections 是数组（`SectionConfig[]`），不应在代码里给每个区块定义独立变量名（如 `ivSections['basic_info']` / `s4Sections['device_fraud']`）。这种硬编码变量名违反了「模板可以有任意数量/类型的数据块」的设计前提。

**改动**：

| 文件 | 变更 |
|---|---|
| `PreVerifyDetail.tsx` | 删除 `ivSections: Record<string, SectionConfig>`，改为 `contentSections` 数组 → `basicSec/idSec/singleSec/crossSec` 按位置访问。导航栏和 Panel 标题全部从 `s.name` 动态派生。 |
| `FraudScheme4Detail.tsx` | 删除 `s4Sections: Record<string, SectionConfig>`，改为 `contentSections` 数组 → `basicSec/identitySec/forgerySec/deviceSec/behaviorSec/gangSec/blkSec/hisSec` 按位置访问。`secDeduct` 改为接受 `SectionConfig` 而非硬编码字符串。导航栏和 Panel 标题全部动态派生。 |

**效果**：

- 报告详情页的导航文字 = 模板配置页中对应分段的 `name` 字段（例如模板里改成"申请者信息"，导航就显示"申请者信息"）
- 不再存在 `ivSections['basic_info'].name` 这样的硬编码变量名路径
- 报告模板配置页后续增删分段，详情页导航和标题自动跟随

**未改动部分**：

- 报告详情页的 `Panel` 内部渲染逻辑（如"用户基本信息"→表格、"用户证件照"→图片列表）仍依赖内容数据（`d.basic` / `d.images` 等），这是数据模型层面的耦合，与显示层的变量命名无关。
- `CreditKimiDetail.tsx` / `DecisionDetail.tsx` 仍有类似硬编码，属于 §7.1 后续待办。
